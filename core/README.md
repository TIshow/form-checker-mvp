# core — 競技に依存しない計測

3D関節データから運動学的な量を取り出す。**純 numpy のみ**に依存し、
3D復元 (GVHMR 等) の環境は要らない。

| モジュール | 役割 |
|---|---|
| `skeleton.py` | SMPL 24関節の定義・体節質量比（De Leva） |
| `geometry.py` | 幾何ユーティリティ（純関数） |
| `kinematics.py` | 重心・床・関節角・体幹・捻転・手の向き・キネティックチェーン |
| `convert.py` | 他の骨格 → SMPL24 の並べ替え（SOMA 77/78。次は MHR 127） |
| `plot.py` | 重心の高さのグラフ（任意依存 matplotlib） |

## 何を置いてよいか

**「どの競技でも同じ意味を持つ量」だけ。** 重心、床、関節角、体幹の傾き、
捻転差、角速度、体格。

**置いてはいけない**のは「その競技だからそう測る」もの — 利き手の決め方、
局面（打点・トップ・リリース）、指標の選択、閾値。それらは
[domains/](../domains/) にある。

## 入力

| 形状 | 内容 |
|---|---|
| (F, 24, 3) | SMPL 24関節の world座標 [m] |

重心と上軸はこの関節から導出する（`compute_com` / `detect_up_axis`）。
**重心計算の定義はこの一箇所だけにある。** 3D復元側は関節までを返す。

## 高さは必ず床から測る（実際に壊れた）

世界座標の原点の置き方は復元手法ごとに違う。GVHMR は床を y≈0 に置くが
TRAM は置かない。原点から測っていたため、同じ動画で打点の高さが
**2.00m と 0.48m** になり、身長が負になって指標が NaN になり、
ビューアが JSON を読めなくなった。

`Kinematics.ground()` が床を返す — **最も低い足の中央値**。最低値だと
一度きりの沈み込みが床になり、跳躍や踏み込みに引っ張られる。

**1つの手法だけで作っていると、その手法の慣習に暗黙に依存する。**
複数を通したから見つかった。

## 平滑化は時間解像度と引き換え

`smooth()` は角速度のノイズを落とすためにあるが、窓を広げると
キネティックチェーンの順序判定に必要な 20〜40ms の分解能も失う。

単一画像モデル（SAM 3D Body など）はフレーム間の一貫性を持たないため、
ジッタをこれで消したくなる。**それは判定そのものを壊す。**
[issue 011](../docs/issues/011-commercial-architecture.md) を読むこと。

## `x_factor` は弱い指標

体節が自分の軸まわりに回る成分は、関節**位置**にほとんど現れない。
`x_factor` は位置から出しているので、回転が主役の競技（ゴルフ・野球）では
特に弱い。Tier C 以上に使わないこと。
