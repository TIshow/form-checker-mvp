# Issue 009: 製品化のライセンス制約（GVHMR と SMPL が非商用）

Status: Open
作成: 2026-08-08

## なぜ今これを書くか

「日本の部活動で使えるように製品化したい」という目標が出た。現在のパイプラインは
**2箇所が非商用ライセンス**で、そのままでは製品化できない。技術的にどれだけ
良くなっても、ここが解けないと出口がない。設計判断（どの手法に乗るか）にも
効き続けるので、先に整理しておく。

## 依存部品のライセンス（2026-08-08 実地確認）

| 部品 | 役割 | ライセンス | 商用 |
|---|---|---|---|
| **GVHMR** | 世界座標の3D復元 | 独自（非商用） | ✗ 個別許諾 |
| **SMPL / SMPL-X** | 人体モデル | MPI 学術ライセンス | ✗ 別途商用契約 |
| **YOLOv8** (Ultralytics) | 人物検出 | AGPL-3.0 | △ 公開 or 有償 |
| HMR2 (4D-Humans) | 体の回帰 | MIT | ○ |
| ViTPose | 2D関節 | Apache-2.0 | ○ |
| DPVO | SLAM | MIT | ○ |

GVHMR の LICENSE 原文（該当部）:

> Permission to use, copy, modify and distribute this software and its
> documentation for educational, research and non-profit purposes only.
> Any modification based on this work must be open-source and prohibited
> for commercial use.
> For commercial uses of this software, please send email to xwzhou@zju.edu.cn

SMPL は商用製品・サービスへの組み込みを明示的に禁止し、加えて**再配布・
サブライセンスも禁止**している。商用窓口は Meshcapade / smpl@max-planck-innovation.de。

## 無償で配る場合はどうか

どちらも**非商用の教育目的は明示的に許可**している。

- SMPL: "non-commercial scientific research, **non-commercial education**, or
  non-commercial artistic projects"
- GVHMR: "**educational**, research and non-profit purposes only"

完全無償・非収益なら該当する可能性がある。ただし:

- **SMPL のモデルファイルは配布できない。** 学校側にインストールさせる形は取れず、
  サーバ側で完結させる必要がある（それでも「サービスへの組み込み」に触れうる）
- GVHMR は「改変物はオープンソースでなければならない」— 自前の改造を
  クローズドにできない

## ★ 有力な回避策: NVIDIA GEM-X + SOMA（2026-08-08 判明）

[NVlabs/GEM-X](https://github.com/NVlabs/GEM-X) は、**GVHMR・SMPL・YOLOv8 の3つを
まとめて置き換えられる**可能性がある。全部が商用可能なライセンスで揃っている。

| | 現行 | GEM-X |
|---|---|---|
| 3D復元 | GVHMR（非商用） | GEM-X コード **Apache-2.0** |
| 重み | — | **NVIDIA Open Model License**（"Models are commercially usable"） |
| 人体モデル | SMPL（非商用） | **SOMA**（NVIDIA独自・77関節） |
| 人物検出 | YOLOv8（AGPL） | **YOLOX**（Apache-2.0）+ ByteTrack（MIT） |
| 2D関節 | ViTPose | **同梱**（SOMA 77点用。自己完結） |
| 学習データ | — | **"trained on NVIDIA-owned data only"** |

依存の第三者ライセンスを全部見たが、**非商用・GPL・Max Planck 由来のものは無い**:
guided-diffusion (MIT) / PyTorch3D・ACTOR (BSD-3・MIT) / YOLOX (Apache-2.0) /
ByteTrack (MIT) / SAM 3D Body (Meta SAM License — royalty-free で商用可、
ただし再配布時の条項と輸出規制の遵守義務あり)。

SOMA 本体も Apache-2.0。README は SMPL モデルファイルについて
「別ライセンスであり同梱できない」と明記しているが、これは **SMPL 相互変換を
使う場合だけ**の話。SOMA 単体で使うなら SMPL は要らない。

### さらに: issue 008 にも効くかもしれない

GEM-X は "handles **dynamic cameras** and recovers **global motion trajectories**"
と明記している。[008](008-moving-camera-slam.md) のカメラ運動問題が、
手法の乗り換えで一緒に解ける可能性がある。

### 精度はどうなのか（GENMO 論文の実測値）

GEM-X は GVHMR との比較を公開していない（評価は自社の MetroSim 検証分割）。
研究版 [GENMO (ICCV 2025)](https://arxiv.org/abs/2505.01425) の Table 1 が
一番近い材料になる。EMDB (24) / RICH (24) の世界座標評価:

| 指標 | GVHMR | GENMO | |
|---|---|---|---|
| WA-MPJPE₁₀₀ (EMDB) | 109.1 | **69.5** | GENMO 36%改善 |
| W-MPJPE₁₀₀ (EMDB) | 274.9 | **185.9** | GENMO 32%改善 |
| RTE % (EMDB) | 1.9 | **0.9** | GENMO |
| Jitter (EMDB) | **16.5** | 17.7 | GVHMR |
| **Foot-Sliding (EMDB)** | **3.5** | 8.8 | **GVHMR 2.5倍良い** |

RICH も同傾向（W-MPJPE 126.3 → 118.6、Foot-Sliding 3.0 vs 6.7）。
**カメラ空間はほぼ互角**（EMDB PA-MPJPE 42.7 vs 42.5, Table 2）。
差がつくのは世界座標化の段だけで、[008](008-moving-camera-slam.md) で
問題を切り分けた場所と一致する。

**Foot-Sliding の差はトレードオフの表と裏。** GVHMR が足の滑りで勝つのは
接地の事前分布が強いからで、それが跳躍を潰している当の仕組み。

- GVHMR: 足を地面に留める → 滑らない → **跳ばない**
- GENMO: 拘束が緩い → 軌跡が正確 → **足が滑る**

跳ぶサーブには GENMO 側が向く可能性があるが、**体重移動の解析には
足の滑りが効く**。指標だけでは決まらない。

**この数字は GEM-X のものではない。** GENMO は SMPL・公開データ込みで
学習しており、GEM-X は SOMA・NVIDIA所有データのみで再学習している。
ライセンスが綺麗なのはその代償を払った結果で、同じ精度が出る保証はない。
論文の限界にも「off-the-shelf の SLAM に依存している」とある。

### ✅ 実測した（2026-08-08）

同じ2クリップを両手法で復元して比べた（`tools/compare_backends.py`）。
**結論: 精度でGEM-Xを選ぶ理由は、我々の素材では見つからなかった。**

自分のサーブ（固定カメラ・60fps）:

| | GVHMR | GEM-X | |
|---|---|---|---|
| 沈み込み → 打点 | 87 → 103 | 86 → 104 | ほぼ一致 |
| 跳躍（足の浮き） | +8.0 cm | +7.4 cm | ほぼ一致 |
| 沈み込み膝角 | 104° | 107° | ほぼ一致 |
| 足の滑り | **105.9** | 198.8 cm/秒 | GVHMRが良い |
| 打点の肘角 | 131° | 172° | **GVHMRの方が当てはまる** |

Zverev（動くカメラ・4.8〜10.3秒）:

| | GVHMR | GEM-X | |
|---|---|---|---|
| 打点フレーム | 139 | 139 | 完全一致 |
| 跳躍（足の浮き） | +3.6 cm | **+2.0 cm** | **どちらも再現しない** |
| 足の滑り | 627.4 | **440.6 cm/秒** | GEM-Xが良い |
| 沈み込み膝角 | 73° | 86° | — |

**独立した2手法が局面・膝角・体幹をほぼ揃えた**のは、どちらの基本部分も
信頼できることの裏付けになる。打点フレームが完全一致したのは特に強い。

**肘角は目視で決着した。** 打点フレームを等倍で切り出すと、GVHMR の
メッシュは実際の腕に重なり手がグリップ位置にあるのに対し、GEM-X の腕は
左にずれて実際の腕がはみ出す。**GVHMR の当てはまりが良い。**
（縮小画像では逆に見えたので、この種の判断は必ず等倍で行うこと。）

**足の滑りは素材によって逆転する。** 論文の傾向（GVHMRが2.5倍勝つ）は
自分のクリップでは再現したが、Zverev では逆だった。一般化できない。

### ❌ 動作の質が実用に足りない（これが決め手）

指標より先に、**動きを見た判断が決定的だった**。ユーザーの評価:

> 自分の動画も zverev の動画も少し GVHMR の方が再現度が高い。
> 特に GEM-X の方は砲丸投げのようなフォームになっている。

**GEM-X 自身が出力した世界座標レンダ**（こちらのコードを通らない）で確認したところ、
同じ傾向が出た。自分のクリップの沈み込み〜打点:

- GVHMR: 体が伸び上がり、腕が高く伸び、体幹が反る。**サーブの姿勢に見える**
- GEM-X: 体が縮こまる。途中で両腕を横に広げる。打点でも体が伸びない。
  **押し出す動作に見える**。体型推定も背が低くずんぐりしている

**関節の取り出しがこちらの誤りである可能性は否定できた。** `poses` の組み立ても
`scale_params` の分割も推測で決めたので疑ったが、GEM-X 自身のレンダが同じなので
復元そのものの性質。

**「砲丸投げ」の正体はラケットドロップの欠落だった。** ユーザーの補足:

> 打点に向かってラケットヘッドが下がるような動きになってないってことですね。

手首→手のベクトルが鉛直からどれだけ倒れるかで測ると（手の向きがラケットの
シャフト方向の近似になる。0°=真上、180°=真下）、自分のクリップで:

| | 沈み込み→打点の推移 | 最大の落ち込み |
|---|---|---|
| GVHMR | 44→43→43→48→**81→110→108**→67→10 | **116°** |
| GEM-X | 45→51→55→56→53→43→53→**72**→33→17 | **72°** |

**GVHMR は 116° まで落ちてから打点で 10°（真上）へ振り抜く**——ラケットヘッドが
背中側へ落ち、そこから加速する動き。**GEM-X は 72° 止まりで、ドロップが無い。**
（Zverev では逆に GEM-X の方が深い 141° vs 119° なので、素材によって出方は違う。）

**当初こちらが測っていた指標では、この欠陥を検出できなかった。** 打点の腕の高さ・
上腕の傾き・手首の高さ・肘角、どれも GEM-X が特に悪いとは出ず、むしろ良く出る
項目もあった。**数字は正常に見えるのに動きが間違っている**——製品化では最悪の
失敗の仕方になる。

教訓として2つ残す:

1. **動作の質は目で見て確かめること。** 関節角の一致は、動作が正しいことを
   意味しない。今回はユーザーの目が指標の欠落を見つけた。
2. **ラケットドロップを指標に入れること。** サーブのキネティックチェーンの核心
   なのに、膝・肘・体幹しか測っていなかった。上の測り方（手の向きの鉛直からの角度）
   がそのまま使える。ラケット追跡（[006](006-racket-tracking.md)）まで待つ必要はない。

### ⚠️ GEM-X には VO（カメラ運動推定）が同梱されていない

**「dynamic cameras を扱える」は、公開デモだけでは検証できない。**

`scripts/demo/demo_soma.py` で `paths.slam` に書き込む箇所は2つあるが、
**どちらも単位行列**（＝カメラ静止）を書く:

```python
if cfg.static_cam:
    eye = 単位行列 → slam へ保存
elif not Path(paths.slam).exists():
    Log.warning("[Preprocess] VO unavailable. Falling back to static camera")
    eye = 単位行列 → slam へ保存        # 同じ
```

DPVO も DROID-SLAM もリポジトリに無い。`-s` を外しても結果は変わらず
（実測: 跳躍 2.0cm vs 2.1cm）、事前計算済みの軌跡ファイルを**自分で用意する
前提**になっている。GENMO 論文の「off-the-shelf SLAM に依存する」と一致する。

**これは比較の前提を変える。** GVHMR は DPVO を統合して同梱しているので、
動くカメラへの対応という点では**現状 GVHMR の方が完成度が高い**。
GEM-X に乗り換えるなら、SLAM は自前で用意することになる。

### 跳躍問題（[008](008-moving-camera-slam.md)）は手法を変えても解けなかった

Zverev は影の位置から明確に滞空しているのに、**両手法とも 2〜3.6cm しか
浮かせない**。「GVHMR の接地事前分布が原因」という仮説だけでは説明がつかず、
共通の原因（両者とも接地・静止の推定に依存する設計）か、カメラ運動が
両方に効いているかのどちらか。008 の案D（カメラ空間との比較）は
GEM-X が `body_params_incam` を返すので、そのまま実行できる。

### 確かめていないこと（残り）

ライセンスは確認済みだが、**使えるかどうかは別**。評価が要る。

1. **跳躍を再現するか。** 008 の核心。GVHMR は潰していた。同じ2本
   （自分のサーブ / Zverev）で比べれば一発で分かる
2. **足が滑らないか。** 上の表のとおり GENMO はここが弱い。滑ると
   接地と体重移動の判定が濁る。`tools/make_compare.py` の
   `quality()` が既に立位の足の高さを見ているので、指標は流用できる
3. **精度が足りるか。** 膝・肘・体幹の角度が GVHMR と同等以上か
4. **手が使えるか。** 77関節に手が入っている。テニスならグリップや
   手首の使い方に直結する（[006](006-racket-tracking.md) のラケット追跡にも効く）
5. **移行コスト。** `analysis/serve.py` も `web/avatar.js` も **SMPL の24関節前提**。
   SOMA 77関節への対応表を作る作業が要る
6. **計算資源。** Modal のイメージを作り直すことになる

### 評価の進め方

Modal に GEM-X のイメージを立て、既存の2クリップを流す。判断材料は
**跳躍が出るか・足が滑らないか・関節角が妥当か**の3つ。ここが通れば、
下の交渉（GVHMR / SMPL）はどちらも不要になる。

## ✅ TRAM も評価した（2026-08-08）— 結論: GVHMR 以外に選択肢が無い

TRAM（MIT、GENMO 論文の EMDB 評価で GVHMR を上回る）を同じクリップで試した。
`backend/reconstruct_tram.py`。ユーザーの評価:

> やっぱり GVHMR の方が再現度高いですね。

自分のサーブ（同一クリップ・60fps）:

| | GVHMR | TRAM | |
|---|---|---|---|
| 打点フレーム | 103 | 103 | 完全一致 |
| 沈み込み | 87 | 86 | ほぼ一致 |
| 跳躍（足の浮き） | +8.0 cm | +21.2 cm | TRAM が大きい |
| 足の滑り | 105.9 | 172.8 cm/秒 | GVHMR |
| 打点の肘角 | 131° | 148° | — |
| **ラケットドロップ** | **116°** | **72°** | **GVHMR** |

### ラケットドロップは目視判断を予測できる

3手法での結果:

| | ラケットドロップ | ユーザーの評価 |
|---|---|---|
| GVHMR | **116°** | 最も再現度が高い |
| TRAM | 72° | 劣る |
| GEM-X | 72° | 劣る（「砲丸投げ」） |

**順位が一致した。** 当初測っていた指標（腕の高さ・上腕の傾き・肘角）は
むしろ GEM-X を良く見せ、判断を誤らせた。**この指標は解析層に入れる価値がある**
——バックエンドの選択とは無関係に、フィードバックとしても核心。

### 副産物: 解析層のバグが見つかった

TRAM は世界座標の**原点の置き方が GVHMR と違う**（床を y≈0 に置かない）。
高さを原点から測っていたため、身長が負になり指標が NaN になり、
ビューアが JSON を読めなくなった。床（最も低い足の中央値）から測るよう修正。

**1つの手法だけで作っていると、その手法の慣習に暗黙に依存する。**
複数を通したから見つかった。

## 現状のまとめ

| | ライセンス | 動作の再現 | 判定 |
|---|---|---|---|
| **GVHMR** | **非商用** | **◎ 唯一実用に足る** | 品質は必要条件を満たす唯一 |
| TRAM | MIT | △ | 商用可だが品質不足 |
| GEM-X | Apache-2.0 | ✗ | 商用可だが品質不足 |
| WHAM | MIT | 未評価 | 論文値では GVHMR より劣る |

**品質で選べるのは GVHMR だけ、商用で選べるのは GVHMR 以外だけ**、という
噛み合わない状態。ここが製品化の唯一の分岐点になった。

## 進め方（順番が大事）

**GEM-X の評価を最優先にする。** 通れば以下の交渉は全部不要になり、
通らなければ以下に戻る。

### 1. GVHMR の商用可否を当たる（費用ゼロ）
`xwzhou@zju.edu.cn` に照会する。**ここが一番読めない**（大学研究室の裁量で、
可否も条件も事前に分からない）。GEM-X が使えなかった場合の退避先なので、
返事に時間がかかることを見込んで早めに出しておくのはあり。

### 2. YOLOv8 を差し替える（費用ゼロ・交渉不要）
人物検出なので代替が効く。**YOLOX / RT-DETR / RTMDet はいずれも Apache-2.0**。
差し替えれば AGPL の問題は消える。これは可否を待たずに着手してよい。

### 3. SMPL の商用ライセンスを取る（費用の問題）
Meshcapade が扱っており、経路は確立している。**可否ではなく費用の交渉**。
WHAM も TRAM も SMPL ベースなので、手法を変えても回避できない。事実上の前提条件。

## GVHMR が NG だった場合

残りは全部許諾型なので、**世界座標化の段だけが問題**になる。

- ViTPose + HMR2 でカメラ空間の姿勢は取れる（MIT / Apache-2.0）
- 足りないのは「重力に対する向き」と「世界座標での軌跡」
- ここを自前で作るのは研究プロジェクトになる。安易に見積もらないこと

なお [008](008-moving-camera-slam.md) で分かったとおり、**跳躍が失われているのは
まさにこの世界座標化の段**。自前で作るなら、その弱点を直せる可能性はある。
