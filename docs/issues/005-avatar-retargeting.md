## 目的

復元した自分のサーブの動きを **VRMアバターに反映して再生**する。

分析機能ではなく **フック（見て楽しい・人に見せて伝わる）** としての位置づけ。
「自分のサーブがアバターで動く」は技術に関心のない人にも一瞬で伝わる。

## なぜ技術的に筋が良いか

モーションを別キャラへ移す（リターゲット）とき、**関節位置**を渡すと体格差で破綻するが、
**関節の回転**を渡せば体型が違っても成立する。

そして GVHMR の出力はまさに回転である。

```
smpl_params_global:
  global_orient  (F, 3)   体全体の向き（axis-angle）
  body_pose      (F, 63)  = 21関節 × 3（axis-angle）
  transl         (F, 3)   位置
  betas          (F, 10)  体型
```

現在の `_gvhmr_joints` はこれを**関節位置に変換した後に捨てている**だけなので、
回転をそのまま返せば素材は揃う。データ量も現在の関節列（208×24×3）と同程度。

## 実装方針

- アバター形式: **VRM**（VRoid Studio で自作可能）
- ライブラリ: **`@pixiv/three-vrm`** — 既存の Three.js ビューアに追加できる
- VRM は humanoid ボーンが規格化されているため、対応表を書けば流し込める
- three-vrm の **normalized bone node**（T-pose に正規化されたリグ）を使うと補正が楽になる想定

### ボーン対応表（SMPL → VRM）

`body_pose` は pelvis を除く21関節。`body_pose[i]` が SMPL joint `i+1` に対応する。

| SMPL | VRM | | SMPL | VRM |
|---|---|---|---|---|
| (global_orient) | hips (回転) | | 11 R_foot | rightToes |
| (transl) | hips (位置) | | 12 neck | neck |
| 1 L_hip | leftUpperLeg | | 13 L_collar | leftShoulder |
| 2 R_hip | rightUpperLeg | | 14 R_collar | rightShoulder |
| 3 spine1 | spine | | 15 head | head |
| 4 L_knee | leftLowerLeg | | 16 L_shoulder | leftUpperArm |
| 5 R_knee | rightLowerLeg | | 17 R_shoulder | rightUpperArm |
| 6 spine2 | chest | | 18 L_elbow | leftLowerArm |
| 7 L_ankle | leftFoot | | 19 R_elbow | rightLowerArm |
| 8 R_ankle | rightFoot | | 20 L_wrist | leftHand |
| 9 spine3 | upperChest | | 21 R_wrist | rightHand |
| 10 L_foot | leftToes | | | |

## 難所（ここに時間が溶ける）

1. **レストポーズの差 ← 最大の壁**
   SMPL の基準姿勢と VRM(T-pose) の基準姿勢が違うため、回転をそのまま入れると
   **腕がねじれた不自然な姿勢**になる。ボーンごとに基準姿勢の差分（オフセット回転）を
   求め、`q_vrm = q_offset⁻¹ · q_smpl · q_offset` の形で補正する必要がある。
   「動いたが気持ち悪い」の原因はほぼこれ。
2. **座標系・前方向の規約**（up軸は実測済みだが、VRM側の前方向規約は実装時に確認する）
3. **体型差**: アバターは頭が大きく手足が短い → **打点の高さなどは物理的に別物**になる
4. **ラケットが無い**: 現在ラケットは未追跡なので素振り状態。手ボーンにラケットの
   モデルを付ければ見た目は作れる

## 分析との切り分け（重要）

アバターは **「見る」ため**であり、**「測る」のは実データ（SMPL）**。
アバターの打点高さなどを指標にすると体型差で意味が壊れるため、
指標算出は既存の `analysis`（実データ由来）から動かさない。表示レイヤーのみの追加とする。

## ライセンス

VRMモデルには個別の利用規約（改変・二次配布・商用の可否）がある。
**VRoid Studio で自作したモデルなら問題なし。** 配布モデルを使う場合、
特に SNS へ投稿するなら規約を確認すること。

- [x] ボーンごとのオフセット回転を算出して適用
- [x] 打点・沈み込みのフレームで姿勢が破綻していないか確認
- [x] 骨格と重ねて整合を確認

**判明したこと: 差は「ボーンごと」ではなく、まず「体全体の向き」だった。**
VRM と SMPL の基準姿勢は約 **180°ヨー**で食い違っていた。これをボーンごとの
最短回転に肩代わりさせると、ほぼ反対向き同士の回転になって**軸が不定**になり、
ねじれが暴れる。そこで二段構えにした:

1. 背骨（上方向）と左右の上腕（右方向）から体の基準フレームを作り、
   全体の回転 `W` を先に求める
2. その上で各ボーンの残差 `A[i]` を出し、補正は `A[i]・W`

結果、補正角は **平均 84.8°→11.8°、最大 178.7°→28.9°**（前腕は 2.1°）に低下。

`d_rest_smpl` は外部入力なしで求まる。`G[i]⁻¹·(現在の骨の向き)` が全フレームで
一定になる性質を使い、手元のデータから逆算している。

## 受け入れ条件

- 自分のサーブが VRM アバターで再生され、**沈み込み→伸び上がり→打点**が自然に見える
- 実データの重ね合わせ動画と見比べて、動きが明らかに破綻していない
- 既存の分析・指標に一切影響しない（表示レイヤーの追加に留まる）
- 骨格表示とアバター表示を切り替えられる

## リスク / 未解決

- レストポーズ補正が想定より手強い可能性（この種の作業で最も一般的な躓き）
- VRM の仕様バージョン差（0.x / 1.0）による前方向・ボーン名の違い
- モバイルでの描画負荷（アバターは骨格より重い）
- 手指は `body_pose` に含まれない（SMPL-X の手パラメータは別）ため、握り表現は別途

## スコープ外

- アバターを使った分析・指標算出（**やらない**。上記「分析との切り分け」参照）
- モーションの書き出し（VMD/FBX等）や他ツール連携
- 複数アバターの比較表示
