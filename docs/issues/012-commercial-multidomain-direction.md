# Issue 012: 商用化と複数分野への展開方針

Status: Proposal（提案。モデル採用・実装着手の決定ではない）
作成: 2026-09-20
対象: テニス／ゴルフ／オペラ
根拠: 現行コードの読解、既存検証記録、同日の公式資料・SNS原投稿・公開コード調査

新規モデルの推論、精度比較、現行Web APIの稼働確認は今回実施していない。

## 目的と優先順位

スマホで記録した動作を見返し、過去の自分や他の人と比較して、練習・指導に使えるサービスを作る。
3D復元は、奥行きが必要な比較・計測を可能にするための手段。商用利用の条件と、各指標に必要な精度を両方満たす。

| 分野 | 当面の位置づけ | 最初に検証する価値 |
|---|---|---|
| ゴルフ | 商用化の主軸。最も早く事業につながりそうというユーザーの見立てに基づく | コーチがレッスン前後のスイングを比較し、生徒へ説明できるか |
| テニス | 個人利用を維持 | 既存の解析・比較を継続し、基盤変更による破損も確認する |
| オペラ | 相談者との限定的な検証 | 同じフレーズの姿勢・音声・本人／指導者評価を同期して比較できるか |

ゴルフの購入者・価格・対象指標は未確定。コーチ向けは初期仮説であり、利用検証で確かめる。
オペラの「姿勢を変えれば響きが改善する」は検証対象。姿勢だけから響きの良し悪しや原因を断定しない。

## 推奨構成

```text
スマホ動画／音声・撮影条件
    ↓
認証された受付・原本保存・区間選択・品質確認
    ↓
交換可能な推定処理（2D姿勢／3D姿勢／必要な道具・ボール／音声）
    ↓
推定結果の保存（時刻・座標系・骨格定義・品質・モデル版）
    ↓
分野別の局面検出・計測・比較（Python）
    ↓
動画・骨格・数値・注釈・履歴の画面
    └─ 必要な場合のみ、根拠画像と計測結果をAstraへ渡して説明
```

- Python／NumPy、ModalのGPU実行、既存のThree.js表示を活用する。
- アプリは内部モジュールを分けて育てる。モデルごとの依存・GPU環境は分離する。
- 利用者向けの保存にはオブジェクトストレージ、履歴・利用者・ジョブの管理にはDBを設ける。
- 推定結果を保存し、指標や画面の変更だけならGPU推論を再実行しない。
- 2Dは同条件の動画比較・注釈・イベント表示に使う。奥行きが必要な指標は検証済みの3D経路に限定する。
- 相対的な3D姿勢と、床・コートを基準にした位置・移動を区別する。表示できる3Dと、計測できる3Dも区別する。
- 単眼で必要な精度が得られない指標は、提供範囲を絞るか、校正した同期2視点や別の計測手段を検討する。

## プロジェクト・リポジトリ・ディレクトリ

事業仮説・利用者・課題・評価データは分野別に管理し、コードは当面1リポジトリに置く。
分野ごとの長期ブランチは作らず、変更単位のブランチを使う。

```text
analysis/
  core/           # 時間、座標、幾何計算、品質、共通データ定義
  tennis/         # サーブ固有の局面・指標・ルール
  golf/           # ゴルフ固有の局面・指標・ルール
  voice/          # 歌唱の特徴と姿勢の対応
backend/
  api/            # 受付、認証、ジョブ・履歴・結果取得
  providers/      # 推定モデル／外部サービスごとの実行・変換
web/
  shared/         # 再生、骨格表示、注釈など
  tennis/
  golf/
  voice/
experiments/      # 分野別・モデル別の検証
tests/
docs/issues/
```

構成は移行先の案。空の機能を大量に作らず、ゴルフを追加する過程で必要な共通処理を抽出する。
各分野がcoreを使い、coreは各分野に依存しない。
権限・契約・担当チームの独立性が必要になった時点でリポジトリ分割を再検討する。
商用提供の実行環境には、提供用途の条件を満たした依存だけを含める。ディレクトリ分離だけで利用条件が変わるわけではない。

## 推定モデルの選び方

| 候補 | 位置づけ | 採用前に確認すること |
|---|---|---|
| SAM 3D Body＋MHR | 新規の3D評価候補 | ゴルフでの精度、フレーム間の安定性、床基準の扱い、採用する依存一式の利用条件 |
| GEM-X＋SOMA | 既存接続を使う比較候補 | サーブでの再現不足を踏まえ、ゴルフで必要な動作を個別評価する |
| ViTPose+／MediaPipe等 | 2D推定・比較・撮影案内の候補 | 遮蔽、高速動作、モデル資産・APIの条件、処理費用 |
| GVHMR＋必要な商用許諾 | 他候補で必要な品質が出ない場合の選択肢 | GVHMR、SMPLなどの依存を含む許諾条件・費用 |

現時点で商用モデルの採用は未決定。既存のGEM-X検証を成功扱いにせず、同じ失敗を見落とさない。
GVHMRの既存結果も正解データとは扱わない。新たな商用開発に利用する場合の条件は別途確認する。
TRAM本体のMIT表記だけでは、使用するSMPLモデルまで商用利用可能とは判断できない。

## Astraの位置づけ

Astraは必須依存にしない。3D姿勢推定の代替として採用しない。

1. 開発時: ラケット・クラブ・ボールなどの自動ラベル案、実装支援。確認したラベルで専用モデルを学習する。
2. 利用時: 必要な動画区間の出来事の解釈、検証済みの計測結果の説明・質問対応。
3. 常時処理: フレームごとの座標推定・指標計算は専用モデルと固定したコードを使う。

自動ラベルにも誤りがあるため、未確認の出力を正解扱いしない。
説明層に渡す値・画像・時刻を限定し、数値と根拠の対応を検証する。
JSON形式が正しいことと、助言内容が正しいことは別に評価する。

## 現行コードからの修正点

| 優先度 | 現状・対象 | 修正方針 |
|---|---|---|
| 最優先 | `analysis/__init__.py`は常にServeKinematicsを呼ぶ | 分野別の入口を作り、汎用計算とサーブ固有処理を分離。既存CLIは互換入口を維持 |
| 最優先 | `backend/reconstruct.py:run_job`はGVHMRとサーブ解析を直結 | 推定結果の保存を境界に、復元・解析・表示を分ける |
| 最優先 | SMPL24の添字、配列＋fps＋up_axisが中心 | ネイティブ骨格を保持し、名称・階層・単位・座標系・時間・欠損・版を明示 |
| 最優先 | `detect_phases()`のcontactは手首高さの最大フレーム | 「接球候補」として由来を保存。動画上で手動修正できるようにし、確定接球と区別 |
| 最優先 | `contact_height_m`はそのフレームの手首高さ | 手首高さという定義を表示。ボール接触点の実測と混同しない |
| 最優先 | 頭と足の平均方向から上軸を推定し、足の位置から床を推定 | 重力・床・スケールの由来と品質を保存。復元できない量は判定・比較に使わない |
| 最優先 | `feedback.py`は角速度ピーク順から「力の伝わる順序」を断定 | 観測した運動学的な差と、力学的な解釈・指導仮説を分離。Tier Aの断定条件も再検証 |
| 高 | fps閾値など一部の品質保護はあるが経路ごとに異なる | 指標ごとに利用可否・理由を計算し、単体解析／比較／集計で共通化 |
| 高 | `skeleton.js`はSMPL24とサーブ局面の色に依存 | 骨格定義と局面情報を引数で渡す。表示用変換と計測用座標を分離 |
| 高 | 比較は沈み込み・打点の対応が中心 | 分野別の局面、手動補正、実時間と局面整列、実寸と正規化の切替を追加 |
| 外部試用前 | Web APIはbase64投入、提示コードに利用者認証・ジョブ所有者検証がない | 認証・認可、所有者付きジョブ、アップロード上限、利用量制限、保存・削除、失敗時対応を追加 |
| 外部試用前 | 履歴は生成ファイル中心 | 利用者・セッション・試行・原本・解析版・指導者の注釈を永続化 |
| 追随 | READMEやissueに古い状態・強い科学的断定が混在 | 実装と検証結果に合わせて更新。過去の検証履歴は残す |

特に、重心は人体モデルの仮定を使った推定値であり、左右の荷重や床反力を直接測っていない。
「高fpsなら指摘が正しい」「既定の連鎖から違えば欠点」とはせず、測定の確かさと指導根拠を別々に扱う。
これは指導ルールを別の未検証ルールに置き換える提案ではなく、断定を支える検証を追加する提案。

## 保存するデータの最小要件

- 原本・切り出し区間・利用者／セッション／試行ID。
- 再生時刻と実動作時刻の対応。撮影fps、ファイルfps、スロー倍率の情報と由来。
- 2D／3Dの区別、単位、骨格定義、座標系、床・スケールの校正情報。
- 観測点／推定点／補間点、欠損、信頼度が提供される場合はその値。信頼度未提供を高信頼とみなさない。
- モデル・重み・前処理・骨格変換・解析ルールの版。
- 局面の推定候補と人の修正、指標の値・定義・利用可否・理由、コーチの注釈、実際の結果。

過去比較は同じ定義・解析版で行う。異なる版なら再解析するか、比較条件が違うことを示す。
同名の関節を並べ替えるだけで、異なる人体モデルの計測値が同等になるとは仮定しない。

## 開発順序と完了条件

| 段階 | 作業 | 次へ進む条件 |
|---|---|---|
| 1. 商品仮説・評価方法 | ゴルフの利用者、最初の3〜5指標、撮影条件、許容誤差を決める | コーチと何を比較できれば役立つか共有できる |
| 2. 最小限の境界整理 | 分野別入口・推定結果の保存・品質・局面修正を追加 | 既存テニスを維持しつつ別モデルを同条件で比較できる |
| 3. モデルと権利の検証 | SAM 3D Body等をゴルフで評価。依存一式の版・利用条件を記録 | 対象指標の精度・再現性・処理費用・利用条件が揃う |
| 4. 外部試用の準備 | 認証・履歴・保存・削除・利用量制限・比較画面 | 許諾された素材で、利用者が自分の試行を安全に見返せる |
| 5. 小規模な利用検証 | コーチの説明・利用継続・支払意思を確かめる | 利用価値と運用費が事業仮説に合う |
| 6. 追加投資 | 道具・ボール検出の学習、Astraの説明、オペラ拡張 | 実際の不足と改善効果が明確になったものから進める |

最初のモデル比較は2週間程度で一度判断する区切りを提案する。納期や精度達成の保証ではない。
素材の目安は5〜10人・50〜100スイング。人物・撮影日単位で開発用と評価用を分け、近接フレームの漏洩を避ける。
局面の時刻、指標の誤差、失敗率、誤った指摘、再現性、処理時間・費用を記録する。
3D誤差を判定する一部の素材には、校正した同期2視点や別の計測手段を使い、その基準側の誤差も考慮する。
合成テストは計算・互換性の確認に使い、実動画での正確さや指導効果の証明とは分ける。

## 当面の投資対象から外すもの

- Astraを全フレームに適用する常時解析。
- 3分野を同時に完成させる開発、汎用の自動矯正AI、人体モデルのゼロからの学習。
- モデル評価の前提にならないNext.js化、マイクロサービス化、リポジトリの分割。
- 比較・計測の価値を確かめる前のアバター品質向上。

- [Move API規約](https://developers.move.ai/policies/terms-of-use/)：出力をAIへ入力する用途の制限がある。有料APIでも今回の用途への適合を確認する。
