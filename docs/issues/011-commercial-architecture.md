# Issue 011: 商用化に向けた構成の転換（三脚前提・蒸留・結果計測）

Status: Open
作成: 2026-09-20

## なぜ今これを書くか

[009](009-licensing-for-productization.md) は「品質で選べるのは GVHMR だけ、商用で
選べるのは GVHMR 以外だけ」という噛み合わない状態で止まっていた。

その後に2つのことが起きた。

1. **三脚固定に統一すると決めた**（カメラが動く素材を捨てた）
2. **外の事例を調べた**（GPT-6 Astra 周辺のスポーツ解析）

この2つが、009 の行き詰まりの前提そのものを崩す。**「商用可で世界座標3D復元」
という問題は、解く必要がなくなっている。** 本 issue はその組み替えを記録する。

## 1. 目的（確定している要件）

| | 要件 | |
|---|---|---|
| 入力 | スマホ1台の2D撮影 → 3D化 | 三脚固定・較正は許容できる |
| 比較 | 他人との比較・過去の自分との比較 | |
| ライセンス | 商用利用可 | ここが唯一の障壁だった |

展開先は3つ（[前回の層分割](#関連)を参照）。**3つとも固定設営が許される環境**
であることが、以下の設計の土台になる。

- テニス … 現状は個人利用。部活動への無償提供＋スポンサー収益を構想
- ゴルフ … 最も早く収益化できそう
- オペラ … 歌手からの相談（姿勢と響きの関係）

## 2. 転換点1 ─ 三脚に統一した時点で、世界座標化は不要になっている

009 に自分で書いた測定値:

> **カメラ空間はほぼ互角**（EMDB PA-MPJPE 42.7 vs 42.5, Table 2）。
> 差がつくのは世界座標化の段だけ

三脚ならカメラの外部パラメータが動画中ずっと一定なので、

> **カメラ空間の3D姿勢 × 固定の回転1回 = 世界座標の3D姿勢**

GVHMR の唯一の優位（DPVO でカメラ運動を解き、重力を推定し、世界座標へ持っていく段）
は、**このユースケースでは使わない**。SLAM も VO も要らない。

**必要なのは「世界座標3D復元」ではなく「カメラ空間の3D関節」+「床の較正」** に
下がる。009 が「自前で作るのは研究プロジェクトになる」と警告した段を、
**作らずに回避する**のが本筋。

### テニスはコートが較正物体になる

コートの寸法は規格で決まっている（シングルス 23.77 × 8.23 m）。ラインから
ホモグラフィを1枚求めれば、**地面平面の座標がメートルで出る**。チェッカーボードは要らない。

ゴルフは打席のマット、オペラはレッスン室の床で同じことをする（既知寸法の物体が要る）。

## 3. 転換点2 ─ VLM は「測る」道具ではなく「ラベルを作る」道具

GPT-6 Astra（OpenAI, 2026-09-03）を使ったスポーツ解析の事例を5件確認した。
**3Dバイオメカニクスをやっているものは1件も無く、5件中4件は姿勢推定に Astra を
使っていない。**

| 事例 | やっていること | Astra の役割 |
|---|---|---|
| [@measure_plan](https://x.com/measure_plan/status/2097715692069859769) テニス | ボール速度・ストローク分類・コース | **ラベル付けのみ**。推論は fine-tuned RF-DETR |
| [@jeremyparkphd](https://x.com/jeremyparkphd/status/2097450619594281144) ダンス同期 | 2人の2D姿勢を毎フレーム比較 | **不使用**。ViTPose+ Large |
| [@jeremyparkphd](https://x.com/jeremyparkphd/status/2100000445607588163) クライミング | 接触時間・ホールド選択・**過去の自分との比較** | **不使用**。ViTPose+ Large + SAM 3.1 |
| [@roboflow](https://x.com/roboflow/status/2098082396306346295) テニス | 得点判定・イン/アウト・ストローク種別 | **意味理解**。幾何計測ゼロ |
| [@LearnOpenCV](https://x.com/LearnOpenCV/status/2096877590204272825) ボール追跡 | Astra で直接追った | **推論に使った → 下記** |

### Astra はフレーム単位の計測には使えない（構造的に）

- **動画を受け付けない。** 5fps に間引いたフレームを画像として送る方式
- 1フレーム 0.02〜0.08 ドル / 約11秒。Roboflow 自身が
  `"Astra is not a per-frame tracker"` と明記
- LearnOpenCV の実測: ボール追跡1本で **11分49秒・787万トークン**

**5fps = 1フレーム200ms。** 本リポジトリの `domains/base.py` は

```python
TH_CHAIN_MIN_GAP_S = 0.05   # 体節間の時間差は 20〜40ms しかない
CHAIN_MIN_FPS = 60.0        # 30fpsでは分解できないので判定しない
```

としている。**サーブの連鎖は全体で約100ms で、Astra の1フレーム間隔の中に
まるごと収まる。** 30fps ですら判定を拒否している領域に対して12分の1の粗さで、
原理的に見えない。Roboflow の評価項目にキーポイント推定の欄自体が無い
（あるのは物体検出 82.1% mAP@50 ＝ バウンディングボックス）。

### 正しい使い方は蒸留

```
Astra（賢い・高い・遅い）  → 少数フレームにラベルを付ける
      ↓ 蒸留
RF-DETR 等（専用・安い・速い） → 全フレームに適用
```

完成後、Astra は一度も動かない。@measure_plan のパイプラインがこれそのもの。

## 4. 転換点3 ─ ライセンスは3層ある。蒸留すると全部消える

| 層 | 例 | |
|---|---|---|
| コード | Apache-2.0 | 誰でも見る |
| 学習済み重み | 別ライセンスのことがある | たまに見落とす |
| **学習データ** | **Human3.6M は学術利用のみ** | **ほぼ全員が見落とす** |

2D→3D lifting の主要な系統（MotionBERT 等）は H36M で学習している。
**コードが Apache でも、重みが学術限定データ由来なら商用は危ない。**
009 で GEM-X を評価した軸（"trained on NVIDIA-owned data only"）は正しかった。

**蒸留の副次効果として、この3層が自動的に消える。** Astra が付けたラベルで
自分のデータを訓練したモデルは自分のもの。H36M も SMPL も経路に出てこない。

### 商用可で揃う部品

| 部品 | 役割 | ライセンス |
|---|---|---|
| ViTPose+ / RTMPose | 2D関節 | Apache-2.0 |
| RF-DETR | 物体検出（ボール等） | Apache-2.0 |
| SAM 3.1 | セグメンテーション | Meta SAM License（royalty-free 商用可） |
| Astra 等の VLM | ラベル生成・イベント検出 | API 利用規約のみ |
| 蒸留した自前モデル | 実行時の推論 | **自社所有** |
| 三脚較正 + 三角測量 | 3D化 | 自前（数十行） |

**非商用なのは GVHMR による世界座標復元だけで、それは §2 で不要になった。**

## 5. 提案する構成

```
① 意味・イベント   VLM（5fps・JSON強制）           商用OK  ← 手作業の置き換え
      ↓ 蒸留
② 物体・ボール     fine-tuned RF-DETR（全フレーム）  商用OK  Apache-2.0
③ 2D関節          ViTPose+ / RTMPose（全フレーム）  商用OK  Apache-2.0
④ 3D化            三脚較正 ＋（2台なら）三角測量     商用OK  自前
⑤ 比較・統計       既存資産                          ← 差別化
⑥ 表示            既存のビューア
```

### カメラ2台が本命かもしれない

2台 + Apache-2.0 の2D姿勢 + 古典的な三角測量 = **学習3D事前分布ゼロで計量的に
正しい3D**。深さを推定ではなく測定するので、**単眼のどの手法より正確**。
SMPL も H36M も要らず、ライセンス問題が構造的に消滅する。

代償は設営（較正）だけで、**3ドメインとも固定設営が許される**。
既製品として [Pose2Sim](https://github.com/perfanalytics/pose2sim)（OpenSim まで繋ぐ）
がある。ライセンス要確認。

### ⑤ が差別化である理由

市販の姿勢分析アプリは2°の違いを赤く塗って「改善点」と表示する。それがノイズか
どうかを言わない。本プロジェクトは指標ごとの測定ばらつきを実測している
（打点の高さ CV 1% / 足の浮き CV 42%）。**「差がないときは差がないと言う」**
——Tier A/B/C の規律と合わせて、技術ではなく姿勢の差別化で、真似されにくい。

## 7. 進め方（優先順位）

**0. 受け入れテストを固定する**（30分）
   ラケットドロップを `tests/` に入れ、「自分のクリップで 100° 以上」を
   候補バックエンドの合格条件にする。GVHMR 116° / TRAM 72° / GEM-X 72° で
   目視評価の順位を再現した唯一の指標。以降の手法評価が自動になる。

**1. VLM でクリップ分割と in/fault を置き換える**（半日・約10ドル）
   5fps + タイムスタンプ + JSON強制。出力は `{"time": 3.4, "type": "SERVE"}` 形式。
   手作業と誤検出が同時に消える。

**2. コートのホモグラフィを求める**（半日）
   ラインから4点。地面がメートルになる。④ の前半でもある。

**3. ボール検出を蒸留で作る**（2〜3日）
   VLM で数百フレームにラベル → RF-DETR を fine-tune → 全フレーム。
   **打点位置（手首から既知）＋バウンド地点（地面＝ホモグラフィが効く）＋経過時間**
   で平均速度が出る。接球速度そのものではないが、進歩を追うには足りる。

**4. 比較UXの実装例を読む**
   `github.com/jeremyipark/vision-demos`（他人との比較 / 過去の自分との比較、両方ある）

**5. 三脚較正で世界座標化する段を書く**（1日）
   これが通るとバックエンドへの要求が「世界座標」から「カメラ空間」に下がる。

**6. カメラ2台を試す**（1日）

**7d. ゴルフは GEM-X が有力**（2026-09-21）
   同じゴルフ映像を GEM-X にも通したら、前傾角が GVHMR と一致した
   （アドレス 14.7° vs 15.5°。SAM 3D Body は 34.2°）。局面もリード膝も一致し、
   肘のジッタは 2.8°/f（GVHMR 2.2、SAM 3D Body 8.2）。
   **独立した2手法が 15° で揃ったので、SAM 3D Body の 34° は復元の前傾バイアス
   であって、カメラの傾きではない**——7c の切り分けがこれで付いた。
   GEM-X を落としたのはテニスのラケットドロップ（速い腕の鞭動作）で、ゴルフに
   その失敗モードは無い。時系列モデルなので足も滑らない。ライセンスは
   Apache-2.0 + NVIDIA 所有データで最も綺麗。**ゴルフの出荷用は GEM-X を
   第一候補に置き直す。** 野球（速い腕）とオペラは引き続き SAM 3D Body。

**7c. 奥行き方向の傾きは単眼では決まらない**（2026-09-20）
   ゴルフ（正面撮り）の前傾角が GVHMR と 18.7° 食い違った。一方、横撮りの
   投球・打撃の体幹の傾きは 1〜2° で一致。単眼の復元は「前に傾いた体」と
   「上を向いたカメラ」を区別できず、GVHMR は時系列と重力の事前分布で解くが
   SAM 3D Body は解けない。**撮り方で回避する**：測りたい量が画像面内に
   来る向きから撮る（前傾角なら横、捻転なら正面）。正面で撮るなら直立の1秒で
   まとめて打ち消す。床の平面からの較正は SMPL24 の足でも MHR のかかと・
   つま先でも成立しなかった（GVHMR 基準と一致しない）。

**7b. 足が床を滑る問題**（2026-09-20）
   4競技すべてで、SAM 3D Body の復元は立っているだけの人の足が床の上を
   滑って見えた（フレームごとの並進のゆらぎ。錨の足が 10秒で 2〜5m）。
   `core/anchor.py` で接地足を留めて並進を組み立て直し、滑りを 0 にした。
   局面の検出は骨盤相対・もう片方の足相対に統一したので、固定の有無で
   結果は変わらない。GVHMR が内部でやっている拘束の後処理版で、跳躍を
   再現しない限界も同じ。

**7a. 打撃でも確認**（2026-09-20）
   SAM 3D Body は**スロー映像で一度破綻した**（1フレームの動きが数mm、ジッタが
   数cm）。`core/filter.py` で撮影fpsに応じて平滑化すると GVHMR と局面・指標が揃った
   （接地 f97/f99、インパクト f164/f159、ストライド 0.73/0.69、手速 7.4/7.9 m/s）。
   通常速度の映像では平滑化の窓が1になるので投球の結果は変わらない。
   床の平面から重力を推定する案も試したが、足の軌跡が一直線に近く法線が
   定まらない（GVHMR の打撃で 28° ずれた）ので捨てた。カメラの傾きは投球 1.4°、
   打撃 2.3° で、いずれも問題にならなかった。

**7. ~~GEM-X をカメラ空間で測り直す~~ → ✅ SAM 3D Body + MHR で決着**（2026-09-20）
   GEM-X が内部で使っている SAM 3D Body を単体で通したら、野球で GVHMR と
   リリースフレームが一致し、目視の関門も通った。ライセンスは SAM License +
   Apache-2.0。詳細は [009](009-licensing-for-productization.md)。
   **以後、人に見せる結果は SAM 3D Body で作り、GVHMR は検証の基準にだけ使う。**

**8. GVHMR に商用照会**（0円・並行）`xwzhou@zju.edu.cn`

### なぜ 1〜3 が先頭なのか

42本やって分かったのは「フォームの数字は安定している（打点の高さ CV 1%）のに、
in/fault との差が Holm 補正を越えない」だった。**原因は姿勢の精度ではなく、
結果データが二値で17対25しかないこと。** ボール速度という連続量が入れば
二値比較ではなく回帰になり、検出力が桁で変わる。

**3D計測の価値を初めて検証可能にするのが 1〜3 で、そこが最短経路。**

## 8. やってはいけないこと

- **世界座標化を自前で研究開発する。** 009 の警告は正しい。三脚で回避する
- **コードのライセンスだけ見て商用判断する。** 学習データまで遡る
- **VLM をフレーム単位の計測に使う。** §3 のとおり構造的に無理
- **「スマホ1台でどこでも」を要件に入れる。** 3ドメインとも固定設営できる。
  この要件を捨てるだけで、技術的難易度もライセンス問題も同時に下がる
- **2つ目の競技を作る前に汎用基盤を設計する。** 汎用層は設計せず抽出する

## 9. 未解決のまま残るもの

- **跳躍が再現されない**（[008](008-moving-camera-slam.md)）。GVHMR・TRAM・GEM-X
  の3手法とも 2〜3.6cm しか浮かせない。三脚でも解けるとは限らない
- **ラケット追跡**（[006](006-racket-tracking.md)）。手の向きで代用中
- **SMPL の商用ライセンス**。GVHMR を使い続けるなら Meshcapade との交渉が残る
- **オペラの技術的可否**。SMPL 24関節に頸椎の詳細も肋骨も顎も無い。
  SMPL-X でも喉頭は取れない。設計の前に実機検証が要る

## ドメイン分割（2026-09-20 実施）

1リポジトリのまま `core/`（競技非依存の計測）と `domains/`（競技ごとの
局面・指標・判定）に分けた。テニス・ゴルフ・野球・オペラの4ドメインがある。

- テニスは既存の値を**完全に再現**（沈み込み87→打点103、ラケットドロップ
  116.3/72.3/72.1、跳躍 +8.0/+7.4/+21.2cm）。振る舞いを変えない移行だった
- 新しい3競技は**指標のみで判定ゼロ**。`evidence_needed` に
  「判定を入れる前に確かめること」を列挙してある
- `test_unimplemented_domains_make_no_threshold_claims` が、
  出典の無い判定が入り込むのを機械的に止める

設計の詳細は [domains/README.md](../../domains/README.md)。

**[012](012-commercial-multidomain-direction.md) は `analysis/core` `analysis/tennis`
… という入れ子の配置を提案している。** 実装したのはトップレベルの
`core/` `domains/` で、入れ子の有無以外は同じ（core は競技に依存せず、
競技が core を使う）。どちらでも中身は変わらないので、配置は好みで決めてよい。

**012 が提案していて、まだ入れていないもの:**

- ネイティブ骨格の保持（SMPL24 に潰さず MHR 127 のまま持つ）
- 打点を「候補」として由来つきで保存し、動画上で手で直せるようにする（[001](001-contact-and-phase-detection.md)）
- 観測した運動学的な差と、力学的な解釈・指導仮説を分離する
- 復元と解析の間に保存の境界を置く（`backend/reconstruct.py` の直結を解く）
- 外部試用の前の認証・認可・保存・削除
