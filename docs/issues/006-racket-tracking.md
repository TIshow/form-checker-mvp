# Issue 006: ラケットを追跡する

Status: Open
Created: 2026-07-26
GitHub: [#6](https://github.com/TIshow/form-checker-mvp/issues/6)
関連: 打点検出は [001](001-contact-and-phase-detection.md) / アバターの飾りラケットは [005](005-avatar-retargeting.md)

---

## 背景

現在ラケットは**まったく追跡していない**。アバターに持たせているものは
前腕の延長方向にモデルを固定しただけの**飾り**（[005](005-avatar-retargeting.md) フェーズD）で、
実際のラケットの位置・向きとは無関係。

## 追跡できると何が得られるか

飾りが本物になるだけではない。**今は測れない指標が測れるようになる。**

| 得られるもの | 現状 |
|---|---|
| **ラケットヘッド速度** | ❌ 測定不能。サーブで最も知りたい量のひとつ |
| **真の打点** | △ 「手首が最も高いフレーム」で代用中（[001](001-contact-and-phase-detection.md)） |
| ラケット面の向き | ❌ 回転量・方向の議論ができない |
| 打点と体の位置関係 | △ 手首基準でしか言えない |
| アバターが本物のラケットを持つ | ❌ 飾り |

特に**ラケットヘッド速度**は、キネティックチェーンの「力が末端まで伝わったか」を
結果として示す量なので、既存の指標と噛み合う。

## 使えるもの（ゼロからではない）

1. **COCO の学習済みYOLOに `tennis racket` クラスがある。**
   すでに Volume に置いてある `yolov8x.pt` は COCO 80クラスの学習済みで、
   `tennis racket`(38) と `sports ball`(32) を含む。**まず追加学習なしで試せる。**
2. **カメラ内部パラメータ `K_fullimg` が復元結果に入っている。**
   GVHMR の出力 `.pt` に `K_fullimg (F,3,3)` がある。2D検出を3Dへ持ち上げる際に使える。
3. **剛体仮定が強力。** ラケットは手に固定されているので、手に対する相対姿勢は
   ほぼ一定。毎フレーム自由に解く必要はなく、**握りのオフセット(6DOF)を一度推定すれば**
   ラケット姿勢 = 手の姿勢 × 定数オフセット で表せる。

## アプローチ（段階的）

### 案A: 剛体オフセットのみ（安上がり）
手のボーン姿勢に対する固定オフセットを推定して付ける。2D検出は
オフセット推定にだけ使い、毎フレームは追跡しない。
- 利点: 実装が軽い。検出が飛んでも破綻しない
- 欠点: 手首のひねりが SMPL の精度に依存する。グリップ変化は表現できない

### 案B: 2D検出 → 3Dへ持ち上げ（本命）
各フレームでラケットを2D検出し、`K_fullimg` と手の3D位置を使って
ラケットの3D姿勢を推定する。剛体仮定を事前分布として使い、
再投影誤差を最小化して時間方向に平滑化する。
- 利点: 実際の動きが取れる。ヘッド速度が出せる
- 欠点: 検出が落ちる区間の扱いが必要

### 案C: 専用モデルの学習（最後の手段）
ラケットの**キーポイント**（グリップ端・ヘッド先端）を学習させる。
バウンディングボックスより姿勢推定に向くが、アノテーションのコストが大きい。

## 難所

1. **モーションブラー ← 最大の壁**
   スイング中のラケットは激しくぶれ、**一番知りたい打点付近でこそ検出が落ちる**。
   30fps では特に厳しい。[001](001-contact-and-phase-detection.md) と同じ結論で、
   **120/240fps 撮影が前提条件**になる可能性が高い
2. **細くて薄い形状**。フレームは細長く、背景（フェンス・ネット）と紛れやすい
3. **遮蔽**。体の後ろに回る局面（ラケットドロップ）で見えなくなる
4. **手首の精度**。SMPL の `body_pose` は手首までで、指は含まれない。
   剛体オフセットの基準となる手の姿勢自体に誤差がある
5. **速度の微分ノイズ**。ヘッド速度は位置の微分なので、追跡のばらつきが増幅される

## 作業計画

### フェーズ A: 既存YOLOで検出できるか確かめる（最初にやる・安い）
- [ ] 手元のサーブ動画に `yolov8x.pt` をそのまま流し、`tennis racket` の検出率を測る
- [ ] **打点付近**で検出できているかをフレーム単位で確認（ここが本質）
- [ ] 落ちるなら原因を切り分ける（ブラー / 解像度 / 遮蔽）
- この結果しだいで案A〜Cのどれに進むかを決める

### フェーズ B: 剛体オフセットの推定（案A）
- [ ] 検出できたフレームから、手に対するラケットの相対姿勢を推定
- [ ] アバターの飾りラケットを、推定したオフセットに差し替える

### フェーズ C: 3D姿勢の復元（案B）
- [ ] `K_fullimg` を復元結果から返す（現在は返していない）
- [ ] 2D検出 + 剛体仮定 + 再投影誤差最小化で毎フレームのラケット姿勢を推定
- [ ] 欠測区間の補間・平滑化

### フェーズ D: 指標化
- [ ] ラケットヘッド速度を算出し、レポートに追加
- [ ] 打点の定義を「ラケットとボールの接触」に置き換える（[001](001-contact-and-phase-detection.md) と統合）

## 受け入れ条件

- 打点付近を含めてラケットが追跡できている（検出率を数値で示す）
- ラケットヘッド速度が算出でき、値が現実的な範囲にある
- アバターのラケットが実際の動きに追従する
- 追跡できない区間を「できない」と正直に扱う（[001](001-contact-and-phase-detection.md) の
  fps 制約と同じ姿勢。測れないものを測ったことにしない）

## リスク / 未解決

- **30fps ではブラーで成立しない可能性が高い。** その場合、この issue は
  120/240fps 撮影とセットになる
- ヘッド速度の妥当性を検証する基準がない（比較対象がない）。
  文献値と桁が合うかの確認に留まる可能性
- 案C に進む場合、アノテーションのコストが跳ね上がる

## スコープ外

- ボールの追跡（打点検出は [001](001-contact-and-phase-detection.md) の打球音を先に試す）
- スピン量の推定（ボール側の問題）
- ガット面の詳細なシミュレーション
