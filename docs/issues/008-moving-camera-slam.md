# Issue 008: カメラが動く素材で世界座標が壊れる（跳躍が再現されない）

Status: Open
作成: 2026-08-07

## 症状

Zverev のサーブ動画を復元すると、**骨格が跳ばない**。実際の動画では打点直前に
明確にジャンプしているのに、復元では足が地面から 2.9cm しか離れず、
しかも駆動中は逆に **下がる**（−4.6cm）。

比較のため自分のクリップ（固定カメラ）では足が +8.0cm 上がり、跳躍が出ている。

## どこで失われているか（2026-08-07 追記・当初の見立てを修正）

当初は「カメラ運動が原因」と書いたが、切り分けたところ**もっと手前で分かる**ことがあった。

**姿勢推定（カメラ空間）は跳躍を正しく捉えている。** `render_1_incam.mp4`（メッシュを
元動画に重ねたもの）を打点前後で拡大すると:

- 足の**影が足から離れている** → 本人は確かに滞空している
- **復元メッシュの足は実際のシューズに乗ったまま追随している** → 推定は滞空を追えている

にもかかわらず `render_2_global.mp4`（世界座標）では足が床に張り付いている。
つまり**失われるのはカメラ空間 → 世界座標の変換段階**であって、姿勢推定ではない。

これは切り分けとして重要で、対処の選び方が変わる:

- カメラ運動が原因なら → SLAM（案A）で直る
- GVHMR の接地事前分布が跳躍を潰しているなら → **SLAM を入れても直らない**

現時点でどちらとも断定できない。傍証として、**カメラが完全に静止している自分の
クリップでも足の浮きは 8.0cm** しかない（Zverev は 3.6cm）。静止カメラでも
潰れているなら、原因は接地事前分布側に寄る。

### 先にやるべき安い実験

`backend/reconstruct.py` は `smpl_params_global` しか返していない。
**`smpl_params_incam` も返す**ようにすれば、カメラ空間の並進と世界座標の並進を
直接比べられ、上の二択が数値で決まる。復元1本ぶんの費用で済み、
DPVO のビルド（案A）に着手する前に必ずやる価値がある。

副産物として、静止カメラのクリップならカメラ空間の上下動から
**跳躍の高さを測れる**可能性がある。

## カメラ運動そのものについて

`backend/reconstruct.py` は GVHMR を **`-s`（静止カメラ）固定**で呼んでいる。

```python
["python", "tools/demo/demo.py", f"--video={src}", "-s"]
```

`-s` は SLAM を回避して速く安く済ませるための指定で、**カメラが動かない前提**。
この前提が崩れると、カメラの動きが人物の動きとして世界座標に足し込まれる。

Zverev クリップで背景の位相相関を取ると、カメラは動いていた:

| 区間 | 横 | 縦 |
|---|---|---|
| 7.30→7.55s | −20px | −12px |
| 8.05→8.30s | −16px | −8px |
| 9.80→10.05s | −32px | +4px |
| 10.30→10.55s | −64px | **+72px** |

合計 588px（画面高さ1918px）。**継続的な横パン**があり、10.3秒以降は
カット切り替わりと思われる大移動。

## 影響範囲（重要）

壊れるのは**グローバル軌跡だけ**で、姿勢そのものは壊れない。

| 使えるもの | 使えないもの |
|---|---|
| 関節角（膝・肘・体幹） | 跳躍の高さ |
| キネティックチェーンの順序 | 世界座標での水平移動 |
| 局面の検出（沈み込み・打点） | 重心の絶対高さ／伸び上がり量 |
| 骨格の見た目の比較 | 物理量（速度・加速度）の絶対値 |

関節角は `body_pose`（体のローカル回転）由来なので、カメラ運動の影響をほぼ受けない。
一方 `transl`（世界座標での並進）は直接汚染される。

## 対処の候補

### A. DPVO を入れて SLAM 経路を使う（本命）
GVHMR は `-s` を外すと DPVO でカメラ運動を推定する。
- 要 Modal イメージ再ビルド（DPVO は eigen + CUDA コンパイル。ビルドが難しい部類）
- 実行時間と費用も増える
- `-s` はオプション化し、素材ごとに選べるようにする

### B. 事前にスタビライズしてから `-s` で回す（安い回避策）
背景の位相相関で毎フレームのずれを測り、逆方向に平行移動して固定カメラの動画を作る。
- 平行移動しか消せない（ズームや回転は残る）
- 主点がずれるので内部パラメータの前提が崩れる（誤差は現状より小さいはず）
- イメージ再ビルドが要らない

### C. カメラ運動を検出して警告だけ出す（最低限、すぐできる）
`tools/make_compare.py` の `quality()` に「カメラが動いている」を追加し、
グローバル軌跡由来の指標（跳躍・伸び上がり）を UI で伏せる。
**誤った数字を出さないという意味では、これが最も重要。**

### D. カメラ空間の並進も返して原因を確定させる（最優先・最も安い）
上の「安い実験」。これをやる前に A や B に時間を使わないこと。
A は「カメラ運動が原因」が正しかった場合にしか効かない。

## 進め方

**D**（原因の確定）→ **C**（誤情報を出さない）は済 → 結果しだいで **B** か **A**。

なお **C は実装済み**（2026-08-07）。`tools/camera_motion.py` が動画から
カメラ運動を測り、`tools/make_compare.py` 経由で比較ビューアの警告に流れる。
世界座標由来の指標（重心の伸び上がり・打点タイミング）は数値を出さず
「— 使えません」と表示する。

関節列だけからカメラ運動を検出する案は**失敗した**ので残しておく。接地足の
水平移動を見たが、自分のクリップ（静止カメラ）47.1cm に対し Zverev 46.6cm で
差がつかない。サーブでは足が本当に動くため、この代理指標は使えない。

## 受け入れ条件

- カメラが動く素材を投げたとき、跳躍や伸び上がりの数値が**黙って出てこない**
- 固定カメラの素材では今までどおり動く（退行しない）
