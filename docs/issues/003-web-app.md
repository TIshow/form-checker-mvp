# Issue 003: Web アプリ化（アップロード → フィードバック + 3Dビューア）

Status: Open
Created: 2026-07-25
GitHub: [#3](https://github.com/TIshow/form-checker-mvp/issues/3)
関連: バックエンドは [002](002-modal-gvhmr-backend.md) の Modal 関数を使う / 指標は [analysis/](../../analysis/)

---

## 背景

CLI（`modal run` → `python -m analysis`）でエンドツーエンドが通ることを 2026-07-25 に確認した
（temp_my_serve.mp4: 打点frame103、重心0.953→1.122m、フィードバック「打点で肘が曲がっています」）。
次は、コマンドを叩けない形でも使えるよう Web アプリにする。

## ゴール（合意 2026-07-25）

動画をブラウザからアップロードすると、**コーチング文＋主要数値**と、
**3Dビューア（骨格を自由視点）** を表示する1画面。

- 履歴DBは今回は含めない（将来の別issue）
- 元動画へのオーバーレイ再生も今回は含めない（レンダリング実装が重い）

## 見せ方の方針（既存の決定を踏襲）

- **生グラフを主役にしない。** 以前「重心の折れ線を見ても意味が分からない」となった反省。
  主役はコーチング文（「打点で肘が曲がっています」等）と、それを支える少数の数値
- **一度に1〜2件**の指摘（`analysis` の作法をそのまま画面に反映）
- 判定に使っていない参考値（体幹の傾き等）は「参考」と明示して主張しない
- fps はユーザーに申告させる（撮影fpsで判定可否が変わるため）。30fpsなら
  キネティックチェーンは「120fpsで撮ると評価できます」と正直に出す

## アーキテクチャ

```
[ブラウザ]  動画アップロード / 結果 + 3Dビューア表示
    │  Vercel（フロント + 薄いAPI）
    ▼  ジョブ投入（非同期。復元は約10分）
[Modal]   reconstruct 関数（既存）→ gv_*.npy 相当を返す
    │  + analysis をサーバー側で実行（純numpyなのでCPU関数でよい）
    ▼
[ブラウザ] 3D関節列で骨格を Three.js 描画 + フィードバックJSON表示
```

- **バックエンドは 002 の Modal 関数を再利用**。今は CLI 入口(`main`)だが、
  Web用に HTTP エンドポイント（`@modal.fastapi_endpoint` 等）を足す
- **待ち時間 約10分**（コールドスタート）への対応が UX 上の要。ジョブ投入→
  ポーリング/通知で「解析中…」を出す非同期フローにする。ライブ即時応答はしない
- 3Dビューアは `gv_joints.npy`（24関節×フレーム）から骨格を描けば軽量。
  フルメッシュ表示にするなら reconstruct が SMPL 頂点も返すよう拡張が要る（本issueでは骨格のみ）

## 受け入れ条件

- ブラウザで動画をアップロードし、コマンドを打たずに結果が見られる
- コーチング文＋主要数値が表示される（生グラフの羅列ではない）
- 3Dビューアで骨格を自由視点で確認できる
- 約10分の待ちが「壊れている」ように見えない非同期フロー
- fps 未対応時（30fps）はキネティックチェーンを「撮り直しで評価可能」と正直に出す

## リスク / 未解決

- **コールドスタート約10分**が UX の最大の課題。非同期前提でも「長い」と感じられる。
  keep-warm はコスト高。イメージ軽量化や L4 での短縮は 002 のスコープ
- body models のライセンス上、公開デプロイ時に第三者が復元を無制限に叩ける形にしない配慮
- 動画アップロードのサイズ・形式の制限
- 3D骨格の座標系（up軸・コート向き未定義）をビューアでどう見せるか

## スコープ外

- 履歴DB・経時変化（将来の別issue）
- 元動画への骨格オーバーレイ再生
- 認証・複数ユーザー
- 打点/フェーズ検出の改善（[001](001-contact-and-phase-detection.md)）
