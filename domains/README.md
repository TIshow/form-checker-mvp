# domains — 競技ごとの局面・指標・判定

計測の中身は [core/](../core/) にある。ここにあるのは「その競技だからそう測る」
部分だけ — 利き側の決め方、局面、指標の選択、閾値。

| ドメイン | 状態 | 備考 |
|---|---|---|
| `tennis_serve.py` | **実装済み** | TIER A 2件 / TIER B 2件 |
| `golf_swing.py` | 指標のみ | 実映像で GVHMR と局面が一致（トップ 109/110、インパクト 118/118）。インパクトは手の最速で代用（[006](../docs/issues/006-racket-tracking.md)）。前傾角はカメラの傾き（実測 14.5°）の較正が要る |
| `baseball_pitch.py` | 指標のみ | 実映像で局面検出を確認済み（2手法で接地が1フレーム差）。連鎖判定は 240fps 以上が前提 |
| `baseball_swing.py` | 指標のみ | 打撃。接地は前進が止まる点、インパクトは手の最速で代用。連鎖判定は 120fps 以上（見積もり） |
| `opera_posture.py` | 指標のみ | 実映像で GVHMR と姿勢の平均値が一致（頭部前方 5.2/2.4cm、体幹 4.6/3.3°）。ばらつき系の指標は単一画像モデルのジッタで 1.5〜3倍大きく出る。音声側（`core/audio.py`）が未実装 |

## ドメインが実装する4つ

```python
side(joints)             # 利き側をどう決めるか
detect_phases(kin)       # 名前つきフレーム（打点・トップ・リリース…）
measure(kin, phases)     # 指標の辞書
judge(metrics)           # 改善点のリスト
```

これだけが競技ごとに違う。保存・比較・表示は全ドメインで共有する。

## 新しい競技を足すとき

1. `NotImplementedDomain` を継承する
2. `measure` まで書く。**`judge` は上書きしない**
3. `evidence_needed` に「判定を入れる前に確かめること」を列挙する
4. `plot_phases` に重心グラフへ注釈する2局面を書く（無ければ空タプル）
5. 出典を確認してから閾値を足す

`test_unimplemented_domains_make_no_threshold_claims` が2〜3を強制する。
tier の文字列だけでは縛れない（判定を書いた本人が "A" と名乗れてしまう）ので、
**出してよい finding の id を `base.py` の連鎖1つだけに限定**し、
`judge` の上書き自体を禁じている。

**根拠のない閾値を置くより、判定しないほうが常に良い。** 下の事故を読むこと。

### `side` の意味は競技ごとに違う

| 競技 | `side` が指すもの | 決め方 |
|---|---|---|
| テニスサーブ | ラケット側 | 手首が最も高く上がる腕 |
| ゴルフ | **リード側**（右打ちなら左） | フィニッシュで手がどちらの肩の上にあるか |
| 野球投球 | 投げる腕 | 手首が最も速く動く方 |
| 野球打撃 | **リード側**（右打ちなら左） | 踏み出しで足首の移動距離が長い方 |
| オペラ | 意味なし | 既定値。左右差は別途測る |

ゴルフだけ反対側を指すので、`kin.idx("elbow")` の意味が変わる。

### 局面は「探す順番」が結果を決める

ゴルフで一度やらかした。**手が最も高いフレーム＝トップ**としたところ、
フィニッシュを拾った。ゴルフのフィニッシュは手がトップと同等以上に
上がるためで、トップ＝インパクト＝フィニッシュが同じフレームに潰れ、
**リード側の判定まで裏返った**（フィニッシュでは伸びている腕が左右逆になる）。

正しい順番は**インパクトを先に決める**こと。

```
インパクト   = 両端を除いた区間で手が最も低いフレーム
トップ       = その手前で最も高いフレーム
フィニッシュ = その後で最も高いフレーム
テイクバック = トップ手前で最低位置にいた**最後**の1枚
```

最後の1枚、というのも実害から来ている。`argmin` だとアドレスで構えている
間の**先頭**が返り、前に立っているだけの映像の長さがそのまま
`tempo_ratio` に乗った（4秒足すと 2.3 → 15.7）。

測れないときは**測れないと出す**。トップとインパクトが潰れたクリップでは
`tempo_ratio` は NaN にする。1フレームに丸めて「2.1」のような
妥当に見える数字を出してはいけない。

## 判定の信頼度を3段階に分ける

閾値の正しさがそのままフィードバックの正しさになる。「何を根拠にその数字を
決めたか」をコード上で区別し、根拠のないものでは断定しない。

| Tier | 根拠 | 扱い |
|---|---|---|
| **A** | 力学的原理。反例が考えにくい | 断定してよい |
| **B** | 文献にプロの実測レンジがある | 参考として提示する |
| **C** | 根拠なし | **判定しない**。数値を表示するだけ |

### なぜこの区別を入れたか

初期実装は体幹の傾きが35°を超えると「傾きすぎです、軸を保ちましょう」と
警告していた。根拠として挙げた「プロは水平から48°傾いている」という値は、論文本文を
確認したところ**存在しなかった**。検索結果の要約から孫引きしたものだった。

閾値の大半は「それらしい」と思った値を置いただけであり、出典として挙げた
論文にその数字があるかを照合していなかった。**出典を書くこと自体が、
実際には無い裏付けがあるように見せる**という、より悪い状態を作っていた。

### テニスサーブの現在の分類

| 指標 | Tier | 根拠 |
|---|---|---|
| キネティックチェーンの順序 | A | 中心から末端へ順に加速するのが効率的 |
| 打点タイミング（重心頂点との差） | A | 落下開始後に打つとエネルギーが逃げる |
| 接球時の肘の伸展 | B | プロは屈曲 30.1±15.9°（関節角 約150°） |
| 沈み込みの膝角 | B | プロのトロフィー時 屈曲 64.5±9.7°（関節角 約115°） |
| 体幹の傾き(接球時) | C | 文献はトロフィー時25.0±7.1°のみ報告。**接球時の基準値が無い**ため判定しない |
| 打点/頭の高さ比 | C | 標準指標ではなく比較対象がない |
| X-factor | C | 研究の大半がゴルフ。サーブでの適正レンジ未確認 |

膝屈曲は個別研究で **45.0°〜82.8°** と幅が非常に大きい。Tier B は
「プロと違うから直せ」ではなく参考情報として提示する。

**角度の定義が一致している保証はない。** 論文がどの基準面・どの体節ベクトルで
測ったかまでは確認できていない。定義が違えば数値を直接比べる意味がないため、
Tier B でも逸脱をもって欠点と断じない。

### 出典の扱い

Tier B に使えるのは、**論文本文を開いてセクション・図番号まで確認した値だけ**。
検索結果の要約を根拠に「文献値」と称してはいけない。

[1] Kinematics characteristics of key point of interest during tennis serve
    among tennis players: a systematic review and meta-analysis.
    Frontiers in Sports and Active Living (2024).
    https://doi.org/10.3389/fspor.2024.1432030

| 使用値 | 確認箇所 |
|---|---|
| 前脚の膝屈曲(トロフィー時) 64.5 ± 9.7° | [1] Section 3.4, Figure 3 |
| 肘屈曲(接球時) 30.1 ± 15.9° | [1] Section 3.6, Figure 7 |
| 体幹傾斜(トロフィー時) 25.0 ± 7.1° | [1] Section 3.4, Figure 2 |

## 設計方針: プロ比較をしない

「プロと比べて差が大きい所を指摘する」は破綻する。プロ同士でもフォームは大きく異なり、
差は必ずしも欠点ではない。体格が違えば同じ関節角度は再現できないし、する必要もない。

代わりに**誰にでも当てはまる力学的原理**で判定する。参照動画も権利処理も不要で、
かつ最も価値の高い指摘が得られる。

| 判定 | 根拠 |
|---|---|
| キネティックチェーンの順序 | 体の中心から末端へ順に加速するのが力学的に効率的 |
| 打点タイミング | 重心が落ち始めてから打つと力が逃げる |

量的指標（膝・肘）は Tier B として文献値を参考表示するに留める。
打点の高さ比・捻転差は Tier C で判定しない。

## フィードバックの作法

- **一度に1〜2件しか出さない**。人は複数の修正キューを同時に処理できず、
  15件の指摘は0件と同じになる
- 優先度は「原理違反 > 大きな逸脱 > 小さな逸脱」
- 判定はルールで決定論的に行う。将来 LLM を使う場合も**文言の生成のみ**に限定する。
  判定を任せると数値を誤解して嘘の助言を作る

## 撮影フレームレートは競技ごとに違う

連鎖の時間差は隣接体節で 20〜40ms しかない。30fps では 1フレーム=33ms あり
**分解できない**ため、`chain_min_fps` 未満では順序を判定せず、
レポートにその旨を明示する。

| 競技 | `chain_min_fps` | 根拠 |
|---|---|---|
| テニスサーブ | 60 | 体節間 20〜40ms に対し2サンプル以上 |
| ゴルフ | 60 | 同上 |
| 野球投球 | **240（未検証）** | 内旋 約7,000°/秒。サーブの2〜3倍速い |
| 野球打撃 | **120（未検証）** | 骨盤→肩→手の時間差は数十ms |
| オペラ | 判定しない | 局面が無い |

実際、この保護が無かった頃は 30fps の実データで「1フレーム差」を根拠に
誤った指摘を出していた。

**投球の240は見積もりであって実測値ではない。** テニスの60と同じ考え方を
より短い時間差に当てはめただけなので、実測で決め直すこと。

## 既知の限界

- **テニス以外は判定を持たない。** 指標は出るがフィードバックは空。
  これは未完成ではなく、出典を確認するまでの正しい途中状態
- **コート座標が未定義**。前後左右が分からないため踏み込み方向を評価できない
- **道具を追跡していない**（[006](../docs/issues/006-racket-tracking.md)）。
  テニスは手の向きで代用できたが、ゴルフのフェース角は代用できない
- **結果を測っていない**（[010](../docs/issues/010-outcome-measurement.md)）。
  ボール速度・コース・ポイントが無いので、フォームと性能を結べない。
  オペラだけは音声で測れる

## 生成AIに改善点を書かせるとき（`analysis/coach.py`）

`judge` とは別の経路。計測値と `domains/<domain>_evidence.py` の根拠表だけを渡し、
JSON で返させ、根拠 id・tier・指標を機械照合する（issue 020）。

- 根拠表の各項目に `tier`（A/B/C）と `verified`（本文確認／未確認）を持たせる
- Tier A/B かつ本文確認の項目に結びついた改善点だけが残る。それ以外は観察に降格
- 負の根拠（「〜との関係は示されていない」）も表に入れ、通説での断定を止める
- 「プロと比べて」は禁止。比較対象が無いことを本文に書かせる
